1 Databases and Database Users (Chapter 1)
1.1 What is a Database
Database and DBMS
A database is a collection of related data with an implicit meaning, representing some aspect
of the real world (a miniworld or universe of discourse).
A DBMS (Database Management System) is a software system that enables users to dene,
construct, manipulate, and share databases.
A database system = DBMS software + the database itself.
1.2 Characteristics of the Database Approach
The database approach diers from traditional le systems in four fundamental ways
1. Self-describing nature (metadata  catalog) The DBMS catalog stores the structure (schema)
of the database alongside the data itself. Any program accessing the database can ask the DBMS
for the structure at run-time.
2. Programdata independence The structure is in the catalog, not hard-coded in programs.
Changing a le's structure (e.g. adding a column) does not require rewriting every application that
uses it.
3. Data abstraction Users see a logical view through a data model; physical storage details are
hidden.
4. Support for multiple views and concurrent multiuser access Dierent users can see dierent subsets of data, and the DBMS handles concurrent access through concurrency control.
1.3 Actors and Workers
Actors on the scene (interact with the database directly)
 Database Administrator (DBA) Manages the DBMS environment  authorises access, monitors
use, buys hardwaresoftware.
 Database Designer Identies data to be stored, designs the schema.
 End Users Casual (ad-hoc queries), NaiveParametric (canned transactions), Sophisticated (analysts), Stand-alone (personal databases).
 Application Programmers  System Analysts Build and maintain applications.
1.4 Advantages of the DBMS Approach
Controlling redundancy; restricting unauthorised access; providing persistent storage; ecient query
processing via indexes and optimisation; backup and recovery; enforcing integrity constraints; multiple
interfaces.

2 Database System Concepts and Architecture (Chapter 2)
2.1 Data Models, Schemas, and Instances
Data Model
A data model is a set of concepts for describing the structure of a database (data types,
relationships, constraints) and the operations on it. Categories
 High-level  Conceptual Close to human perception. Example EntityRelationship
(ER) model.
 Representational (Logical) Used by commercial DBMS. Example Relational model.
 Physical Describes how data is stored on disk.
Schema vs. Instance
Schema (intension) The descriptionstructure of the database  dened at design time, rarely
changes.
Instance (extensionstatesnapshot) The actual data stored at a point in time  changes
with every update.
Analogy Schema = class denition in a programming language; Instance = an object of that
class.
2.2 Three-Schema Architecture (ANSISPARC)
Three-Schema Architecture
The goal is to separate users from physical storage
1. Internal (Physical) level Describes physical storage structures  record formats, indexes, le organisation.
2. Conceptual level Describes the structure of the entire database for the community
of users. Hides physical details. Dened using a conceptuallogical data model (e.g.
relational).
3. External (View) level Individual user views  each describes the part of the database
that a particular user group cares about.
Mappings between levels translate requests and results between adjacent levels.
Data Independence
Logical data independence Change the conceptual schema without changing external
schemas or application programs (e.g. add a new table or column).
Physical data independence Change the internal schema without changing the conceptual
schema (e.g. move data to a dierent disk, change an index structure).
Physical independence is easier to achieve than logical independence.
2.3 Database Languages
 DDL (Data Denition Language) Denes schemas  CREATE, ALTER, DROP.
 DML (Data Manipulation Language) Retrieves and updates data.
 High-level  Declarative (SQL) Species what to retrieve.
 Low-level  Procedural Retrieves one record at a time; must be embedded in a host language.

 VDL (View Denition Language) Denes external views (in SQL, the CREATE VIEW statement
serves as VDL).
2.4 DBMS Architecture and Module Types
Main component modules DDL compiler (processes DDL, stores in catalog), Query compiler
(parses SQL), Query optimizer (chooses execution plan), Runtime database processor (executes
queries, updates), Stored data manager (controls disk access).
2.5 Centralised and ClientServer Architectures (Section 2.5)
Centralised Architecture
All DBMS functionality and data reside on a single machine. Users connect via dumb terminals
that send keystrokes and display output. Simple to administer but cannot scale to large numbers
of concurrent users.
Two-Tier ClientServer Architecture
Functionality split between a client machine and a server machine
 Client runs the application program and user interface. Sends SQL queries to the server
over a network.
 Server (database server) runs the DBMS, processes queries, returns results.
The client communicates using a standard API such as ODBC (Open Database Connectivity)
or JDBC (Java Database Connectivity). Many clients can share one database server.
Three-Tier (N-Tier) ClientServer Architecture
Adds a middle application server layer between the client and the DBMS
1. Presentation tier (client) thin client  web browser or mobile app. Handles only
display and user input.
2. Application server tier (middle tier) webapplication server. Contains business
logic, session management, and security. Sends SQL to the database tier.
3. Database server tier DBMS. Executes queries and manages data.
Advantages the database is never directly exposed to the internet; business logic is centralised
(not duplicated in every client); each tier can be scaled independently (e.g. add more application
servers during peak load).
Most modern web applications (banking, e-commerce, airline reservations) use the three-tier
model.

Exercise 2.14 Architecture for a Web-Based Airline Reservation System
Question Which DBMS architecture would you choose for a web-based system to make airline
reservations and sell tickets Why would the other architectures not be a good choice
Answer Three-tier (n-tier) clientserver.
 Presentation tier Web browser or mobile app. Thin client  no installation required,
works on any device.
 Application server tier Handles business rules (check seat availability, enforce booking constraints, process payments, manage user sessions, enforce fare rules). This tier is
completely separate from the database, so it can be replicated horizontally across many
machines to handle thousands of simultaneous users (e.g. during a sale).
 Database server tier The DBMS stores ights, fares, reservations, and passengers. It is
shielded behind the application server  end users never send SQL directly to the database
(security and integrity protection).
Why not centralised A single machine cannot handle global airline trac; it is a single
point of failure; it cannot scale.
Why not two-tier The database would be directly accessible from client machines (security
risk). Business logic would have to be duplicated in every client application. Poor scalability 
a single database server would be overwhelmed.

3 Data Modeling Using the ER Model (Chapter 3)
3.1 The Role of Conceptual Modeling
A conceptual schema is produced in the rst phase of database design. It describes what data exists
and how it is related, independent of any DBMS or implementation. The ER model is the most widely
used tool for this phase.
3.2 Entity Types, Entity Sets, and Attributes
Entity, Entity Type, Entity Set
An entity is a distinct real-world thing or concept with an independent existence (physical a
person, car; conceptual a company, job).
An entity type denes the structure of similar entities its name and list of attributes. E.g.,
EMPLOYEE(Name, Ssn, Salary).
An entity set is the set of all current instances of an entity type stored in the database.
3.2.1 Types of Attributes
Type Description ER Notation
Simple (atomic) Single indivisible value Ellipse
Composite Divisible into sub-attributes Ellipse with child ellipses
Multi-valued Multiple values for one entity Double ellipse
Derived Computed from other attributes Dashed ellipse
Stored Source from which a derived attr is computed Regular ellipse
NULL Unknown or inapplicable value (no special symbol)
Key Uniquely identies each entity Underlined label
Example EMPLOYEE Entity Type Attributes
Consider the EMPLOYEE entity type
 Ssn simple, key attribute.
 Name composite → {First_name, Middle_initial, Last_name}.
 Address composite → {Number, Street, City, State, Zip}.
 Birth_date stored (simple).
 Age derived from Birth_date (shown dashed).
 Phone_numbers multi-valued (an employee may have  1 phone).
 Salary simple.
3.3 Relationship Types, Sets, and Structural Constraints
Relationship Type, Degree, Role
A relationship type R among entity types E1, . . . , En denes a set of associations between
their entities.
The degree of a relationship is n. Most relationships are binary (degree 2).
In a recursive (self-referencing) relationship, the same entity type appears more than once;
each participation is given a role name to distinguish them.
A relationship can itself have attributes (e.g., the Hours attribute on WORKS_ON).

3.3.1 Cardinality Ratios and Participation Constraints
Structural Constraints
Cardinality ratio (maximum) how many instances of E2 one instance of E1 can be related
to.
 1  1 one-to-one. 1  N one-to-many. M  N many-to-many.
Participation constraint (minimum)
 Total (existence dependency) every entity must participate. Shown by double line.
 Partial entities may or may not participate. Shown by single line.
(min, max) notation More precise. (0, 1), (1, 1), (0, N), (1, N), etc. Species the minimum
and maximum number of relationships an entity participates in.
Example COMPANY Database Relationships
WORKS_FOR between EMPLOYEE and DEPARTMENT N1 cardinality (many employees work
for one department). Every employee must work for a department (total participation on employee side). A department may have zero employees (partial) but typically has one manager.
MANAGES between EMPLOYEE and DEPARTMENT 11. Each department has exactly one manager; each employee manages at most one department.
WORKS_ON between EMPLOYEE and PROJECT MN. One employee can work on many
projects; one project can have many employees. Relationship attribute Hours.
SUPERVISION (recursive on EMPLOYEE) One employee (supervisor) supervises many employees (supervisees). Role names supervisor, supervisee.
3.4 Weak Entity Types
Weak Entity Type
An entity type with no key attributes of its own. It is identied by
1. Its partial key (discriminator) attribute(s) that distinguish weak entities belonging to
the same owner entity. Shown with a dashed underline.
2. Its owner entity type via an identifying relationship type.
The weak entity's full key = partial key + owner's primary key.
Notation weak entity = double rectangle; identifying relationship = double diamond.
Example DEPENDENT weak entity
DEPENDENT (dependent of an employee) has attributes Dependent_name (partial key  dashed
underline), Sex, Birth_date, Relationship.
Two dependents of dierent employees may share the same name, so Dependent_name alone is
not a key.
Full key = (Essn, Dependent_name), where Essn is the owner EMPLOYEE's key.
Identifying relationship DEPENDENTS_OF (double diamond) with total participation on the
DEPENDENT side (a dependent cannot exist without its owner).

4 The Enhanced ER (EER) Model (Chapter 4)
4.1 Subclasses, Superclasses, and Inheritance
Subclass  Superclass  IS-A
When an entity type E has subgroupings of entities with additional attributes or relationships,
we dene
 Superclass The original entity type (E).
 Subclass A meaningful subgrouping (e.g., SECRETARY, ENGINEER are subclasses of
EMPLOYEE).
 IS-A relationship Every member of a subclass is also a member of the superclass.
 Attribute inheritance A subclass entity inherits all attributes and relationship participations of the superclass, plus it has its own additional specic attributes.
An entity may simultaneously belong to multiple subclasses.
4.2 Specialisation and Generalisation
Specialisation vs. Generalisation
Specialisation Top-down design  start from a superclass, dene subclasses by identifying
distinguishing characteristics. E.g., EMPLOYEE → {SECRETARY, ENGINEER, TECHNICIAN}.
Generalisation Bottom-up design  start from multiple entity types that share common properties, merge them into a superclass. E.g., {CAR, TRUCK} → VEHICLE.
4.3 Constraints on Specialisation
4.3.1 Disjointness Constraint
 Disjoint (d) An entity can belong to at most one subclass. Marked with d inside the circle.
Example An employee is either HOURLY_EMPLOYEE or SALARIED_EMPLOYEE, never both.
 Overlapping (o) An entity can belong to multiple subclasses simultaneously. Marked with o
inside the circle. Example A PERSON can be both an EMPLOYEE and a STUDENT.
4.3.2 Completeness Constraint
 Total specialisation Every superclass entity must belong to at least one subclass. Shown with a
double line from superclass to specialisation circle.
 Partial specialisation A superclass entity may not belong to any subclass. Shown with a single
line.
4.3.3 Dening (Predicate-dened) vs. User-dened
 Attribute-dened (predicate-dened) Membership is determined by the value of a specic
attribute. The dening attribute and predicate value are written on the line. E.g., Job_type =
'Secretary'.
 User-dened Membership is explicitly assigned by users; the DBMS cannot determine it automatically.

4.4 Specialisation Hierarchies and Lattices
 Specialisation hierarchy Each subclass has only one superclass (single inheritance tree).
 Specialisation lattice A subclass can have multiple superclasses (multiple inheritance). Called a
shared subclass. Example ENGINEERING_MANAGER inherits from both ENGINEER and MANAGER.
4.5 Categories (UNION Types)
Category
A category (UNION type U) is a subclass that is a subset of the union of two or more dierent
entity types (superclasses). Shown with a U symbol in the circle.
Example OWNER is a category of {PERSON, COMPANY, BANK}. An owner entity is exactly one of
these three types.
Category vs. shared subclass
 Shared subclass entity must be in ALL superclasses (ANDintersection).
 Category entity is in AT LEAST ONE superclass (ORunion).

5 The Relational Data Model (Chapter 5)
5.1 Formal Denitions
Relation Schema, Relation, Degree, Cardinality
A relation schema R(A1, A2, . . . , An) has a name R and a list of attributes A1, . . . , An, each
with a domain dom(Ai).
A relation instance r(R) is a set of tuples (rows), each of which assigns a value from dom(Ai)
(or NULL) to each attribute Ai
.
Degree number of attributes. Cardinality number of tuples.
Key property a relation is a set of tuples  no duplicates, no inherent ordering.
5.2 Relational Model Constraints
Domain, Key, Entity Integrity, Referential Integrity
Domain constraint Each attribute value must be atomic and from dom(Ai).

6.1 The 7-Step Algorithm
Step 1  Strong Entity Types
For each strong entity type E, create a relation R(A1, . . . , An) with all simple attributes. For a

store derived attributes.
Step 2  Weak Entity Types
For each weak entity type W with owner E (Step 1 relation T), create a relation S. Include all
simple attributes of W plus the PK of T as an FK. PK of S = FK (from T) + partial key of W.
Step 3  Binary 11 Relationships
Identify relations S and T for the two entity types. Preferably choose S as the entity with total
participation. Add the PK of T as an FK into S. Also add any relationship attributes to S.
Alternative create a separate relation (less common, but valid when both sides are partial).
Step 4  Binary 1N Relationships
Identify S = relation for the N-side entity type. Add PK of the 1-side entity as an FK in S.
Add relationship attributes to S.
Step 5  Binary MN Relationships
Create a new relation R. Include PK of both participating entity types as FKs. The PK of R
= both FKs combined (unless a subset is sucient). Add relationship attributes to R.
Step 6  Multivalued Attributes
For each multivalued attribute A of entity type E (with relation T, PK K), create a new relation
R(K, A) where K is an FK referencing T. PK of R = (K, A).
Step 7  N-ary Relationships (n  2)
Create a new relation R. Include PK of all n participating entity types as FKs. Add relationship
attributes. The PK of R is typically all FKs combined (but check if any subset suces due to
cardinality constraints).

7.1 Why Normalize
Poor relational schema designs cause update anomalies
 Insertion anomaly Cannot insert data about one entity without data about another.
 Deletion anomaly Deleting data about one entity inadvertently deletes data about another.
 Modication anomaly Updating a fact requires changing multiple rows; if some are missed, the

7.2 Functional Dependencies (FDs)
Functional Dependency
X → Y holds on R if for every legal state r(R)
whenever t1[X] = t2[X] for tuples t1, t2, then t1[Y ] = t2[Y ].
X functionally determines Y , or Y is functionally dependent on X.
An FD is a property of the schema (all possible states), not just one particular table instance.
Determined by the semantics of the data.
Full FD, Partial FD, Transitive FD
X → Y is a full FD if removing any attribute A from X causes the FD to no longer hold.
X → Y is a partial FD if some A ∈ X can be removed and the FD still holds.
X → Z is a transitive FD (via Y ) if X → Y , Y ̸→ X, and Y → Z (and Y, Z ̸⊆ X).
Identifying FD Types
Consider EMP_PROJ(Ssn, Pno, Hours, Ename, Pname, Plocation).
Assume FDs {Ssn, P no} → Hours (full  both are needed), Ssn → Ename (partial on the
PK {Ssn, P no}), P no → {P name, Plocation} (partial on PK).
This schema suers from anomalies if the only employee on a project leaves, the project name
and location are lost (deletion anomaly).
Also consider EMP_DEPT(Ename, Ssn, Bdate, Address, Dnumber, Dname, Dmgr_ssn).
FDs Ssn → Dnumber and Dnumber → Dname. So Ssn → Dname is a transitive FD (via
Dnumber).
7.3 Normal Forms
1NF  First Normal Form
A relation is in 1NF if the domain of every attribute contains only atomic values (no sets, no
nested relations, no repeating groups). Each cell contains a single value.
2NF  Second Normal Form
R is in 2NF if it is in 1NF and no non-prime attribute is partially functionally dependent
on any candidate key.
A non-prime attribute is one that does not belong to any candidate key.

IA6(a) Authors ranked within each publisher
Problem For each publisher, list its senior authors in descending order of book count.
SELECT Publisher , AuthorName
FROM BOOKS
GROUP BY Publisher , AuthorName
ORDER BY Publisher ASC , COUNT () DESC ;
-- COUNT () = number of books by this author with this publisher
-- Note  an aggregate in ORDER BY is allowed even if not in SELECT
How it works GROUP BY Publisher, AuthorName creates one group per (publisher, author)
pair. COUNT() counts books in that group. ORDER BY Publisher keeps the same publisher
together; COUNT() DESC ranks highest-count author rst within each publisher.
IA6(b) Book(s) with the most authors
Problem Books with the highest total author count (senior + co-authors). Handle ties.
WITH AuthorCount AS (
SELECT B . ISBN , B . Title ,
1 + COUNT ( C . JointAuthorName ) AS NumAuthors
FROM BOOKS B
LEFT JOIN COAUTHORS C ON B . ISBN = C . ISBN
GROUP BY B . ISBN , B . Title
)
SELECT ISBN , Title
FROM AuthorCount
WHERE NumAuthors = ( SELECT MAX( NumAuthors ) FROM AuthorCount ) ;
Key points LEFT JOIN ensures books with no co-authors are included (they get COUNT =
0, so total = 1). WITH (CTE) computes counts once and reuses them in the outer query. =
MAX(NumAuthors) handles all ties automatically.

11.6 Actions as Triggers (Section 7.2)
Trigger  Event, Condition, Action (ECA)
A trigger is a stored rule that res automatically when a database event occurs. Its three
components are
 Event the triggering DML operation  INSERT, DELETE, or UPDATE [OF column], applied
BEFORE or AFTER the operation.
 Condition (WHEN clause) optional predicate; the action res only if this evaluates to
TRUE. Can reference NEW (new tuple being insertedupdated) and OLD (old tuple being
deletedupdated).
 Action (BEGIN...END) SQL statements to execute  can update other tables, raise errors,
send notications, etc.
Row-level trigger (FOR EACH ROW) res once per aected row.
Statement-level trigger (default) res once per SQL statement regardless of how many rows
are aected.
Assertion vs Trigger  Key Dierence
An assertion is declarative you specify a condition that must always be true; the DBMS
decides when to check it and always rejects the violating update.
A trigger is imperative you specify an event, an optional condition, and an action to execute.
The action can do anything  update another table, log a record, send a notication, or raise
an error. Triggers are more exible but harder to reason about than assertions.
Listing 4 Trigger prevent salary exceeding supervisor's salary (Exercise 7.4d style)
CREATE TRIGGER SALARY_VIOLATION
BEFORE INSERT OR UPDATE OF Salary , Super_ssn
ON EMPLOYEE

WHEN ( NEW . Salary  ( SELECT Salary FROM EMPLOYEE
WHERE Ssn = NEW . Super_ssn ) )

RAISE_APPLICATION_ERROR ( -20001 ,
'Employee salary cannot exceed supervisor salary ') ;
END;
Listing 5 Trigger automatically log salary changes to an audit table
CREATE TRIGGER LOG_SALARY_CHANGE
AFTER UPDATE OF Salary ON EMPLOYEE

Note
NEW and OLD are special references inside a row-level trigger
 NEW the row as it will look after the operation (available in INSERT and UPDATE).
 OLD the row as it looked before the operation (available in DELETE and UPDATE).
 NEW is not available in DELETE triggers; OLD is not available in INSERT triggers.

11.7 Schema Change Statements (Section 7.4)
ALTER TABLE and DROP
ALTER TABLE modies an existing table schema  adddrop columns, adddrop constraints.
DROP TABLE removes a table entirely.
DROP SCHEMA removes an entire schema.
RESTRICT the operation is rejected if any other schema element (view, constraint, FK)
references the dropped element.
CASCADE the operation also drops all dependent elements automatically.

ALTER TABLE EMPLOYEE

DROP SCHEMA COMPANY CASCADE ;
-- Drop a view
DROP VIEW WORKS_ON1 RESTRICT ;

12.1 Overview of Database Programming Approaches (Section 10.1)
Three Approaches to Database Programming
1. Embedded SQL SQL commands are written directly inside a host-language program (C,
COBOL, Fortran). A precompiler scans the source le, extracts the SQL statements, and
replaces them with calls to the DBMS runtime library. The resulting le is then compiled
normally. SQL is xed at compile time.
2. Function call libraries (SQLCLI, JDBC, ODBC) SQL is passed as a character string
to library functions at runtime. More exible  the query can be built dynamically. JDBC
is the standard Java version; ODBC is the CWindows version; SQLCLI is the standard
C version.
3. Database programming languages (SQLPSM, PLSQL) Extends SQL with procedural constructs (loops, conditionals, variables, exception handling). Stored procedures and
functions live inside the DBMS. Best performance because there is no network round-trip
per statement.
Impedance Mismatch
The impedance mismatch problem arises because SQL is a set-oriented language (a query
returns a table of rows), while host languages like C or Java are record-at-a-time (a variable
holds one value at a time).
Solution use a cursor  a named pointer into a query result set. The program opens the
cursor (executes the query), then fetches rows one by one in a loop, and closes the cursor when
done.
12.2 Embedded SQL in C (Section 10.2)
Embedded SQL Key Syntax Rules
 Every SQL command is prexed with EXEC SQL and terminated with a semicolon.
 Host variables (C variables shared with SQL) are declared inside EXEC SQL BEGIN DECLARE
SECTION ... END DECLARE SECTION.
 Inside an SQL statement, host variables are referenced with a colon prex varname.
 SQLCODE (integer) or SQLSTATE (5-char string) holds the status after each SQL statement 0 = success, 100 = no more rows (SQLSTATE = '02000'), negative = error.
 Cursor lifecycle DECLARE (dene the query) → OPEN (execute it) → FETCH (get one row) →
CLOSE (release resources).
